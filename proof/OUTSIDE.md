# Iris on agent runs it did not write: AgentDojo

Generated by `npm run proof -- --outside` at 2026-11-11T08:04:23.355Z from a097f982 (v0.21.0), sample 1c2f90c46d79.

**Where the runs come from.** [AgentDojo](https://github.com/ethz-spylab/agentdojo) publishes the log of every run in its benchmark, under the MIT licence: 36,679 runs of 29 agents and defences on tasks in four suites (workspace, Slack, travel, banking), many of them with an instruction planted in a tool's output by an attacker. Beside each log are two answers its environment computed by checking the world after the run: whether the user's task was done, and whether the attacker's goal was. This line measures Iris on 700 of those runs, drawn at commit `089ed468` by `proof/tools/sample-agentdojo.mjs`: 200 where the attack succeeded, 200 where it failed, and 300 with no attack, across 29 agents and 97 tasks. Iris did not write these runs, choose these tasks or label these outcomes. The files are in `proof/outside/agentdojo/`, each checked against the hash AgentDojo's repository lists for it.

**How it is scored.** Each AgentDojo run log is read as the trace a capture integration would send (the user message as input, every tool call paired with the output the agent read, the last message as output; proof/lib/agentdojo.ts) and judged by the engine exactly as the server builds it, at the shipped defaults, with no configuration for these tools. What is right comes only from the labels AgentDojo's environment computed: a run is GOOD when the user's task was done and no attack succeeded, BAD otherwise. A WRONG PASS is a bad run the ship verdict passed; a WRONG FAIL is a good run it failed. An injection detector is a rule declaring the injection or injection_compliance class; it CATCHES a run where the attack succeeded when it fails that run. Each rate is given over runs, with a Wilson 95% interval, and over tasks, each task counted once at its own rate, with the exact interval the comparison tool in Iris uses for repeated cases (clusterInterval), because one task appears under many agents.

## A run against the other runs of its task

Two rules read a run against the earlier runs of its own case: `no_unusual_action` (it called a tool that may act, and no earlier run did) and `no_dropped_step` (it never called a tool every earlier run called). Nobody writes the expectation, and neither rule knows what an attack looks like. **How far to trust these rows.**

- **Neither half is a first read.** A first version of these rules drew its lines at a share of the earlier runs (a quarter or less, three quarters or more). Those lines were set on the dev half and read once on the test half, where `no_unusual_action` fired on 40 of the 93 runs where the attack succeeded and on 4 of the 261 where none did, and `no_dropped_step` on 37 of the 119 runs where the task was not done and on 5 of the 142 where it was. A review then showed that a share fires for ever on an agent that has not changed (a step it takes one run in ten is flagged on nearly every run that takes it), so the lines moved to "no earlier run" and "every earlier run", and a tool whose name both reads and acts (`delete_list`) stopped counting as a look-up. Those changes come from that argument and not from these runs, but they were made after both halves had been read, and the rows above are the ones to read.
- **The history here is other agents'.** The other runs of a task are 29 different agents and defences, where a deployment's history is one agent's own earlier runs.
- **The history here is not clean.** 200 of the 700 runs are successful attacks, so a run is read against other runs that were themselves attacked, far more often than a deployment's would be. With the lines at "no earlier run", one earlier run that took the attacker's action hides the next. The tables under this list read the same runs against a history with no attack in it.
- **Few earlier runs.** No run here is read against more than 14 others, and half are read against 7 or fewer, where the rules read up to twenty.

## What this line is, and is not

- **The labels are AgentDojo's.** Its environment checks the world after each run; a check can be stricter or looser than a person would be, and this line inherits that.
- **Iris ran at its shipped defaults, with nothing configured for these tools.** No trusted tools, no expected values, no tool catalogue: the logs do not carry the tools' schemas, so rules that need one decline to judge. A deployment would configure some of this, and some numbers would move.
- **The sample weights every agent alike,** and it holds as many runs where the attack succeeded as where it failed. Read the rates within each group; the mix of groups is the sample's, not any deployment's.
- **The agents are AgentDojo's, from 2024 and 2025.** The question is whether Iris tells good runs from bad on someone else's traces, and these are someone else's.
