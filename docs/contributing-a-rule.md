# Contributing a built-in rule

This is the path a new built-in rule takes from an idea to a shipped, measured, documented rule — end to end, in the order the guards check it. Every step names the file it touches and the test that refuses the PR if the step is skipped. A rule that reaches the end of this page ships with a published precision and recall on [the proof page](https://iris-eval.com/proof), a cell on the capability map, and a name every surface agrees on.

If you want a rule for **your own** deployment rather than for everyone, you do not need any of this: write a [custom rule](custom-rules.md) (eight JSON-declared types, no code) or a [plugin rule](plugins.md) (an ES module, hash-pinned in the config). This page is for rules that ship in the package.

## Before writing code

1. **Say which question it answers.** Every built-in rule answers one of the evaluation questions in `src/eval/questions.ts` (`safe_output`, `within_budget`, `task_completed`, …). If your rule does not answer one of them, it is not a rule yet — open an issue and say what a reader would learn from it that no existing rule tells them.
2. **Say what it needs.** A rule declares its inputs (`needs`: `output`, `input`, `tool_calls`, `cost`, `tokens`, …) and the engine skips it, naming the missing input, when a trace lacks one. A rule that reads something it did not declare is refused by `tests/capability-map-contract.test.ts` ("for every cell's `needs`, the real engine skips the cell's rules when the named input is absent").
3. **Decide the kind and the mechanism.** `kind` is `detection` (finds a fault), `measurement` (reports a number and never decides), or `policy` (enforces a configured limit). `mechanism` is how it works — `pattern`, `lexical`, `formula`, `structural`, … — and it is published on the evaluators matrix, so it must be the truth.
4. **Write the definition before the corpus.** The proof corpus file (step 6) carries a `definition` paragraph that says, in prose, exactly when the rule fails and when it skips. Cases are labelled against that paragraph, never against the implementation — so write the paragraph first, and let the cases find the holes in it.

## The path

Each step is one file or one command. The trace below follows `cost_anomaly` (shipped in 0.14.0), which touches every surface a rule can touch; a rule that reads only `output` skips the steps that do not apply.

| # | Step | File(s) | Refused by, if skipped |
|---|---|---|---|
| 1 | **Implement the rule.** A pure function with the rule object — `name`, `description`, `kind`, `mechanism`, `needs`, `question`, `classes` (the failure classes from `src/eval/failure-classes.ts` it can stamp), `version: 1`, and `evaluate(context)` returning `{ passed, score, message, evidence? }`. Put the logic in its own module when it is more than a screen (`src/eval/cost-anomaly.ts`) and the rule object in the bundle for its category (`src/eval/rules/cost.ts`; the others are `safety.ts`, `relevance.ts`, `completeness.ts`). The bundle's array is what `src/eval/rules/index.ts` exports as `rulesByType`, so adding the object to the array **is** the registration — there is no second list. | `src/eval/rules/<category>.ts`, `src/eval/<rule>.ts` | `tests/unit/eval/rule-metadata.test.ts` (every rule carries the metadata), `tests/claims-eval-rules-counts.test.ts` (the generator's count equals the runtime array) |
| 2 | **Unit-test the rule** on the cases its definition names: the pass, the fail, every skip reason, and the evidence shape. One file per rule. | `tests/unit/eval/rules/<rule>.test.ts` | a new test file changes the test count, so the truthbase must be recaptured (step 9) — `Truthbase regen vs committed` in CI |
| 3 | **Type the evidence** if the rule stamps a new evidence field or reads a new context field (`cost_anomaly` reads a baseline the engine's callers supply). | `src/types/eval.ts` | `npm run typecheck` |
| 4 | **Wire the input** when the rule needs something the engine does not already carry — `cost_anomaly` needed each prior trace's cost, which `src/eval/ingest.ts` and the server's evaluate path already had in the failure log. Skip this step for a rule that reads the trace alone. | `src/eval/ingest.ts`, `src/eval/engine.ts` | `tests/integration/tool-contracts.test.ts` (the `evaluate_output` contract names which rules skip without history) |
| 5 | **Give it a cell on the capability map.** Every registered rule must appear as evidence in at least one `has` or `partial` cell, and the cell's `needs` must be what the rule declares. | `capability-map.json` | `tests/capability-map-contract.test.ts` ("every registered rule … appears in a has or partial cell"; evidence names resolve; `needs` are real) |
| 6 | **Author the proof corpus** — `proof/corpus/<rule>.json`: `schemaVersion`, `rule`, `category`, `family`, `positiveClass`, the `definition` paragraph, `source` (who wrote the cases and when), `labelling` (how the labels were decided and by whom — never by running the rule), `authored`, and `cases[]` of `{ id, rule, label, input, output, notes }` (plus `tool_calls` for trajectory rules). Aim for at least twenty-five cases, balanced, with the hard negatives your definition almost fails. The runner refuses a corpus whose counts do not match its cases. | `proof/corpus/<rule>.json` | `tests/proof/runner.test.ts`, `tests/proof/measurements.test.ts` |
| 7 | **Measure it.** `npm run proof` runs every corpus through the real engine and rewrites `proof/results.json`, `proof/RESULTS.md`, `proof/transcript-results.json` **and** `src/eval/published-accuracy.ts` — the numbers the site, the README and the `iris://` resources quote. Never edit those files by hand; a hand-typed number is exactly what the proof exists to prevent. Then `npm run proof -- --check`, `--check --composite` and `--check --transcripts` must all say OK. | `proof/results.json`, `proof/RESULTS.md`, `src/eval/published-accuracy.ts` | `Proof — rule accuracy regen vs committed` in CI; `tests/proof/published-accuracy.test.ts` |
| 8 | **Name it on every surface that lists rules.** The dashboard's category map (`dashboard/src/components/dashboard/ruleCategories.ts`); the Live Playground's vendored copy of the bundles (`website/src/lib/eval/rules.ts` — copy the changed bundle in and update its sync note); the skill's rule table (`skills/iris-eval/SKILL.template.md`, rendered to both skill files by `npm run llms:render`); the API reference's rule table (`docs/api-reference.md`). | those four | `tests/docs-contract.test.ts` ("both skill files name every shipped rule"; the rule-by-category tables match the engine's bundles), `tests/playground-parity.test.ts` (the vendored copy is byte-identical), `tests/evaluators-matrix.test.ts` |
| 9 | **Regenerate the truthbase and the rendered docs.** From a quiet tree: `npm run claims:generate` → `npm run llms:render` → `npm run mcp-json:render` → `npm run claims:capture-tests` (runs the whole suite; the count lands in `.claims.json`) → `npm run claims:generate` again → `npm run claims:check`, `npm run llms:check`, `npm run mcp-json:check`, `npm run claims:check-hardcoded`. `docs/capabilities.md` and `docs/evaluators.md` are rendered from their `.template.md` by the same step. | `.claims.json`, `docs/capabilities.md`, `docs/evaluators.md`, `website/public/llms*.txt` | `Truthbase regen vs committed`, `Hardcoded-claim scanner` |
| 10 | **Write the CHANGELOG line** under `## [Unreleased]` › `### Added`, opening with the one sentence a reader needs, and say which question the rule answers and what it skips on. The release page is rendered from this file. | `CHANGELOG.md` | `scripts/verify-release.mjs` at release time |
| 11 | **Break your own guard once.** In the PR description, show the unit test red against a deliberate one-line break of the rule, then green again. Every rule PR in this repository carries that pair. | the PR body | review |

## What the PR description says

The description follows the shape of every rule PR here: the question the rule answers and what it needs; the definition paragraph; the corpus (how many cases, who labelled them, against what); the measured precision and recall with their intervals as `npm run proof` printed them (the numbers [the proof page](https://iris-eval.com/proof) will publish); the red run; and the surfaces the rule now appears on. A rule whose measured precision is low ships anyway **if the number is published** — the proof page states what each rule is worth, and a rule that is honest about a 0.7 precision is more useful than one that hides it.

## A change that did not ship, and why that was right

It is in the proof itself. `no_silent_tool_failure`'s acknowledgement test was to be narrowed to require proximity to the failed call's subject (arc 4, A4-12); the change was measured as a shadow beside the shipped rule and came in at a precision lower bound of 52.9% against a pre-committed bar of 85% (the shadow block on [the proof page](https://iris-eval.com/proof)), so it did not land and the negative result stayed published. The bar was set before the corpus existed. Set yours the same way: decide what number would make you abandon the rule, write it in the PR before you measure, and keep the measurement either way.
